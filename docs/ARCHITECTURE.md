# Architecture

[🇪🇸 Versión en español](es/ARQUITECTURA.md)

DeckRemote has two modes. **Xbox 360 mode** (default) presents a wired Xbox 360 controller, so Windows uses XInput and games can send rumble. **Generic mode** presents a plain HID gamepad.

## Pieces

| Piece | Where | Runs as | What it does |
|---|---|---|---|
| `deckremote.py` | `~/DeckRemote/` | `deck`, launched by Steam | Reads the controller, feeds the virtual gamepad, plays rumble, shows the status screen |
| `xinput.py` | `~/DeckRemote/` | `deck` | Xbox 360 controller over raw-gadget: USB descriptors, control requests, input reports, rumble packets |
| `gadget.sh` | `/etc/deckremote/` | `root` via `sudo -n` | `up-xbox` / `bind` (Xbox mode), `up` (generic mode), `down` (remove everything), `status` (`off` / `waiting` / `connected` + bus id) |
| `report_desc.bin`, `report_len` | `~/DeckRemote/` | — | Generic mode's HID report descriptor, generated by `make_descriptor.py` |
| `set_artwork.py` | `~/DeckRemote/` | `deck` | Finds the shortcut's app id in `shortcuts.vdf` and copies the library artwork into `userdata/<user>/config/grid/` |
| usbip-win2 | PC | user | USB/IP client |

## Xbox 360 mode

1. Steam launches `deckremote.sh`, which runs `deckremote.py` with Steam's game environment: Steam Input is active and the physical pad is hidden from SDL.
2. The app runs `sudo -n gadget.sh up-xbox`, which loads `usbip-host`, `dummy_hcd` and `raw_gadget`, adds dummy_hcd's port (for example `5-1`) to usbip-host's match list, and hands `/dev/raw-gadget` to `deck`.
3. `xinput.py` opens `/dev/raw-gadget`, attaches to `dummy_udc.0` and starts answering USB requests as a wired Xbox 360 controller (`045e:028e`, vendor interface `FF/5D/01` with its 17-byte `0x21` descriptor and two interrupt endpoints). The descriptors follow GP2040-CE (MIT).
4. The Deck's own USB stack enumerates the new device first. Its `SET_CONFIGURATION` is refused, so the device never gets configured locally: no `xpad`, no ghost controller in Steam.
5. The app runs `gadget.sh bind`: `usbip bind` hands the device to usbip-host and `usbipd` (host mode) exports it on TCP port 3240.
6. The PC attaches it. Windows configures it, loads its built-in *Xbox 360 Controller for Windows* driver, asks for the XInput capabilities (answered by `xinput.py`) and sets the player LED.
7. A worker thread reads the **"Steam Virtual Gamepad"** with SDL2 every 4 ms. It builds the 20-byte XInput report (buttons, triggers, sticks with Y inverted) and sends it on the IN endpoint whenever it changes, plus a keep-alive every 0.5 s.
8. Rumble packets (`00 08 00 strong weak …`) arrive on the OUT endpoint. The app plays them on the Deck with `SDL_GameControllerRumble` and re-arms them every 0.5 s while non-zero, because XInput holds a level until changed and SDL rumble expires. Rumble is forced to zero when the PC disconnects and when the app exits.

### XInput report (20 bytes)

| Byte | Content |
|---|---|
| 0, 1 | `00 14` (type, length) |
| 2 | D-pad up/down/left/right, Start, Back, LS, RS |
| 3 | LB, RB, Guide, –, A, B, X, Y |
| 4, 5 | Left / right trigger (0..255) |
| 6–13 | LX, LY, RX, RY (int16, Y up = positive) |
| 14–19 | 0 |

## Generic mode

1. `gadget.sh up` loads `libcomposite`, `usb_f_hid` and `usbip-vudc`, creates a configfs gadget `1d6b:0104` with one 13-byte HID function, binds it to `usbip-vudc.0`, starts `usbipd --device` and hands `/dev/hidg0` to `deck`.
2. The app writes 13-byte HID reports (16 buttons, hat, 4 axes, 2 triggers) to `/dev/hidg0`, non-blocking, on every change and at least every 100 ms.

## Common to both modes

- The UI (full-screen Tk) polls `gadget.sh status` every second and shows the PC's IP, read with `ss` from the connections on port 3240.
- On exit (the button, Steam's `SIGTERM` or closing the window) the app stops rumble, sends a neutral report and runs `gadget.sh down`.
- If the app is killed without a chance to clean up (Steam restarting, `SIGKILL`), a tiny **guard** catches it: a transient user unit `deckremote-guard-<pid>`, started with the app, that waits for the app's PID to disappear, runs `gadget.sh down` and exits. It never outlives the app by more than ~2 seconds.
- The **⇄** button saves the other mode and restarts the app in place (`execv`, same PID for Steam).

## Design decisions

### Why not pass through the Deck's real controller?
The first prototype exported the physical controller (`28de:1205`) over USB/IP. That doesn't work well:
- Windows sees it as a keyboard, a mouse and a vendor device. It isn't a gamepad unless Steam is running on the PC.
- The **Steam** and **⋯** buttons belong to that same device, so the Deck loses them, along with any way to exit.
- After it's handed back, Steam on the Deck may not pick it up again until a reboot.

So DeckRemote **creates a brand-new virtual gamepad**, and the Deck keeps its own controller.

### Why only the "Steam Virtual Gamepad"?
- It respects your Steam Input layout, and the Steam / ⋯ buttons stay with Steam.
- The app disables SDL's HIDAPI backend (`SDL_JOYSTICK_HIDAPI=0`) and picks the pad **by name**, because Steam reports it with the same VID:PID as the physical controller. Opening the physical controller directly can leave it in a state Steam doesn't recover from.

### Why raw-gadget on dummy_hcd for Xbox mode?
- Windows' XInput driver needs the controller's 17-byte vendor descriptor of type `0x21`. **FunctionFS** validates type `0x21` as a 9-byte HID descriptor and refuses it. Without it, Windows binds the driver but XInput reports *not connected*.
- **raw-gadget** lets the app answer every request itself. But `usbip-vudc` asks the gadget for its device descriptor synchronously, which a userspace answer can't satisfy.
- So the pad lives on **dummy_hcd** (a local virtual USB port) and is exported with **usbip-host**, the same path USB/IP uses for real devices.
- Tested on SteamOS 3.9: tearing down a half-configured vudc/FunctionFS or vudc/raw-gadget gadget and unloading those modules **crashed the kernel**. The helper therefore never unloads `raw_gadget` or `dummy_hcd`. They stay loaded and idle, and nothing listens on the network.

### Why is the sudo file called `zz-deckremote`?
`sudo` reads `/etc/sudoers.d/` in alphabetical order and applies the **last** matching rule. SteamOS ships `wheel`, which requires a password. A name that sorts after it makes sure the `NOPASSWD` rule wins.

### Nothing in the background
There are no boot services, udev rules or PC tasks. `usbipd` only exists while the app is open. The PC only needs the standard USB/IP client.

## Persistence on SteamOS
- `~/DeckRemote` lives in `/home`, which SteamOS updates never touch.
- `/etc/deckremote` and `/etc/sudoers.d/zz-deckremote` live in `/etc`, which SteamOS keeps across updates (overlay). If a major update ever drops them, just run `install.sh` again.

## Artwork
`tools/make_art.py` draws all the library images procedurally with Pillow (supersampled 3×). The Deck and gamepad silhouettes were tuned against front-view references with `tools/shape_compare.py`, which reports the overlap (IoU) and writes a colour overlay.
