# Architecture

[🇪🇸 Versión en español](es/ARQUITECTURA.md)

## Pieces

| Piece | Where | Runs as | What it does |
|---|---|---|---|
| `deckremote.py` | `~/DeckRemote/` | `deck`, launched by Steam | Reads the controller, writes HID reports, shows the status screen |
| `gadget.sh` | `/etc/deckremote/` | `root` via `sudo -n` | `up` creates the virtual USB gamepad and starts `usbipd --device`. `down` removes everything. `status` prints `off` / `waiting` / `connected`. |
| `report_desc.bin`, `report_len` | `~/DeckRemote/` | — | The gamepad's HID report descriptor, generated by `make_descriptor.py` |
| `set_artwork.py` | `~/DeckRemote/` | `deck` | Finds the shortcut's app id in `shortcuts.vdf` and copies the library artwork into `userdata/<user>/config/grid/` |
| usbip-win2 | PC | user | USB/IP client that attaches `usbip-vudc.0` |

## What happens when you open the app

1. Steam launches `deckremote.sh`, which runs `deckremote.py` with Steam's game environment: Steam Input is active and `SDL_GAMECONTROLLER_IGNORE_DEVICES` hides the physical pad.
2. The app runs `sudo -n gadget.sh up`, which:
   - loads `libcomposite`, `usb_f_hid` and `usbip-vudc`;
   - creates a USB device `1d6b:0104` in configfs (`/sys/kernel/config/usb_gadget/deckremote`) with one 13-byte HID function;
   - binds it to the virtual UDC `usbip-vudc.0`;
   - starts `usbipd --device` as a transient unit (`deckremote-usbipd`), which exports that UDC on TCP port 3240;
   - hands `/dev/hidg0` to the `deck` user.
3. A worker thread opens the **"Steam Virtual Gamepad"** with SDL2 (the controller Steam gives to games). Every 4 ms it writes the buttons, hat, sticks and triggers to `/dev/hidg0`: on every change, and at least every 100 ms. Writes are non-blocking, so the UI never freezes while no PC is attached.
4. The UI (full-screen Tk) polls `gadget.sh status` every second. When a PC is attached it shows the PC's IP, read with `ss` from the connections on port 3240.
5. On exit (the button, Steam's `SIGTERM` or closing the window) the app sends a neutral report and runs `gadget.sh down`.
6. If the app is killed without a chance to clean up (Steam restarting, `SIGKILL`), a tiny **guard** catches it. The guard is a transient user unit `deckremote-guard-<pid>`, started with the app, that waits for the app's PID to disappear, runs `gadget.sh down` and exits. It never outlives the app by more than ~2 seconds.

## HID report (13 bytes, no report ID)

| Bytes | Field | Range |
|---|---|---|
| 0–1 | 16 buttons (bit 0 = A …) | 0/1 |
| 2 | Hat in the low nibble (0–7, 8 = centred) | — |
| 3–4, 5–6 | Left stick X, Y | −32767..32767 |
| 7–8, 9–10 | Right stick Rx, Ry | −32767..32767 |
| 11, 12 | Triggers Z, Rz | 0..255 |

## Design decisions

### Why not pass through the Deck's real controller?
The first prototype exported the physical controller (`28de:1205`) over USB/IP. That doesn't work well:
- Windows sees it as a keyboard, a mouse and a vendor device. It isn't a gamepad unless Steam is running on the PC.
- The **Steam** and **⋯** buttons belong to that same device, so the Deck loses them, along with any way to exit.
- After it's handed back, Steam on the Deck may not pick it up again until a reboot.

So DeckRemote **creates a brand-new virtual gamepad**, and the Deck keeps its own controller.

### Why only the "Steam Virtual Gamepad"?
- It respects your Steam Input layout, and the Steam / ⋯ buttons stay with Steam.
- The app disables SDL's HIDAPI backend (`SDL_JOYSTICK_HIDAPI=0`) and picks the pad **by name**, because Steam reports it with the same VID:PID as the physical controller. Opening the physical controller directly can leave it in a state Steam doesn't recover from.

### Why `usbip-vudc` and not `dummy_hcd`?
With `usbip-vudc` the virtual device never shows up as a local USB device on the Deck, so no Deck driver grabs it, and `usbipd --device` exports it directly.

### Why is the sudo file called `zz-deckremote`?
`sudo` reads `/etc/sudoers.d/` in alphabetical order and applies the **last** matching rule. SteamOS ships `wheel`, which requires a password. A name that sorts after it makes sure the `NOPASSWD` rule wins.

### Nothing in the background
There are no boot services, udev rules or PC tasks. `usbipd` only exists while the app is open. The PC only needs the standard USB/IP client.

## Persistence on SteamOS
- `~/DeckRemote` lives in `/home`, which SteamOS updates never touch.
- `/etc/deckremote` and `/etc/sudoers.d/zz-deckremote` live in `/etc`, which SteamOS keeps across updates (overlay). If a major update ever drops them, just run `install.sh` again.

## Artwork
`tools/make_art.py` draws all the library images procedurally with Pillow (supersampled 3×). The Deck and gamepad silhouettes were tuned against front-view references with `tools/shape_compare.py`, which reports the overlap (IoU) and writes a colour overlay.
